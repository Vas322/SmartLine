# 1. PROJECT

Smartline — веб-приложение для автоматизации учёта активности игроков клана Lineage 2.

Основная задача первой версии:

Telegram-группа
→ Telegram Bot
→ автоматический разбор сообщений
→ PostgreSQL
→ веб-интерфейс
→ статистика
→ экспорт Excel

В дальнейшем проект может расширяться и включать другие функции управления кланом.

Функциональность фортов является первым модулем Smartline, а не определением всего проекта.

# 2. CORE PRINCIPLES

## 2.1 Простота для игрока

Игроки должны продолжать использовать существующую Telegram-группу практически без изменений.

Не переносить основной пользовательский процесс в Telegram Bot.

Telegram используется прежде всего как источник данных.

Основной интерфейс управления системой — веб-приложение.

---

## 2.2 Автоматизация существующего процесса

Система должна автоматизировать существующий процесс, а не заставлять игроков менять привычки.

Основной сценарий:

Игрок пишет сообщение в Telegram
→ Bot получает сообщение
→ система проверяет формат
→ создаётся запись активности
→ КЛ видит данные в веб-интерфейсе
→ КЛ получает статистику
→ данные можно экспортировать в Excel.

---

## 2.3 Не усложнять MVP

Не реализовывать функциональность, которая не требуется текущей задаче.

Не добавлять:

- LLM;
- AI-анализ;
- автоматическое определение смысла описания;
- автоматическое определение форта;
- автоматическое определение волны;
- сложную систему разрешений;
- мобильное приложение;
- SPA без необходимости;
- webhook Telegram без необходимости;
- автоматическую выплату адены.

Новые функции добавляются только после явного утверждения.

# 4. ARCHITECTURE

Использовать стандартную архитектуру Django.

Рекомендуемое разделение:

- models — структура данных;
- views — HTTP/web слой;
- services — бизнес-логика;

- tests — автоматические тесты.

Названия приложений и окончательную структуру определяет Architect.

## 4.1 Thin Views

Django views должны быть максимально тонкими.

Views не должны содержать сложную бизнес-логику.

Плохой подход:

```python
def activity_view(request):
    # десятки строк расчётов,
    # парсинга и работы с бизнес-правилами

Предпочтительный подход:

View
  ↓
Service
  ↓
Model / Repository / ORM

Бизнес-правила должны находиться в services или специализированных компонентах.

4.2 Telegram handler

Telegram handler не должен содержать всю бизнес-логику.

Предпочтительная схема:

Telegram Update
      ↓
Telegram Handler
      ↓
Message Processor
      ↓
Parser
      ↓
Validation
      ↓
Activity Service
      ↓
Database

Parser должен быть независимым от Telegram.

Он должен уметь принимать обычную строку и возвращать структурированный результат либо понятную ошибку.

5. DATABASE

Использовать PostgreSQL.

Django ORM является основным способом работы с базой данных.

Не использовать ручной SQL без необходимости.

Если ручной SQL действительно необходим:

использовать параметризованные запросы;
не использовать конкатенацию SQL;
обосновать необходимость.
6. DATA MODELS

Минимальная предметная область должна предусматривать сущности:

Player
TelegramMessage
Activity
ProcessingError

Также используются стандартные модели Django authentication.

Финальная структура моделей определяется Architect.

7. TELEGRAM MESSAGE UNIQUENESS

Telegram-сообщение идентифицируется комбинацией:

telegram_chat_id
telegram_message_id

Эта комбинация должна быть уникальной на уровне PostgreSQL.

Использовать database-level UNIQUE constraint.

Повторная доставка одного Telegram Update не должна создавать новую Activity.

Принцип:

same chat_id + same message_id
        ↓
не создавать повторную запись
8. TELEGRAM MESSAGE PROCESSING

Обрабатывать только сообщения, текст которых начинается с +.

Начальные пробелы игнорируются.

Пример:

   +1 | деф | Swettka | 11.56 | Первая волна

должен обрабатываться.

Обычные сообщения игнорируются.

Например:

Кто сегодня на форты?

Всем привет

Кто идет на деф?

не должны попадать в систему активностей.

9. ACTIVITY MESSAGE FORMAT

Основной формат сообщения:

+ЧЧ.ММ | ТИП | НИК[,НИК...] | ВРЕМЯ_НАЧАЛА_ВОЛНЫ | ОПИСАНИЕ

Пример:

+1 | деф | Swettka | 11.56 | Первая волна

Порядок полей строгий: количество, затем тип, затем ники, затем время начала
волны, затем описание. Перепутанный порядок считается ошибкой, сообщение не
обрабатывается.

Время начала волны — четвёртое поле, обязательное. Допускаются разделители
"." и ":" (HH.MM или HH:MM): 11.56 и 11:56 — одно и то же время. Если время
начала волны не указано или указано неверно, сообщение считается ошибочным,
Activity не создаётся, а бот отвечает подсказкой.

Поле DESCRIPTION необязательно: допускается сообщение из четырёх частей
+ЧЧ.ММ | ТИП | НИК[,НИК...] | ВРЕМЯ_НАЧАЛА_ВОЛНЫ (без описания).

Примеры:

+1 | деф | Swettka | 11.56 | Первая волна, держали Южный
+1 | деф | Swettka | 11:56
+0,5 | фарм | Ostin, Pocomaxa | 23.10

Поля:

количество;
тип активности;
игровой ник (несколько ников — через запятую);
время начала волны (обязательно);
описание (необязательно).

Разделитель:

|

Пробелы вокруг разделителя не имеют значения.

Все поля после разделения должны быть очищены от начальных и конечных пробелов.

10. ACTIVITY AMOUNT

Значение после + представляет количество часов.

Примеры:

+1     = 1 час
+0,5   = 0,5 часа
+0,3   = 0,3 часа
+2     = 2 часа

Допускаются:

+0,5
+0.5

Они должны интерпретироваться одинаково.

Для хранения количества использовать Decimal.

Не использовать float для количества часов.

Пример:

0.5 часа = 30 минут
0.3 часа = 18 минут
1.0 часа = 60 минут
2.0 часа = 120 минут

Не вводить самостоятельное округление без явного бизнес-правила.

11. ACTIVITY TYPE

Допустимые типы активности:

DEF
FARM
CAST (каст / перекаст)

Регистр не имеет значения.

Например:

деф
Деф
ДЕФ

должны преобразовываться во внутреннее значение:

DEF

То же относится к FARM и CAST.

Синонимы каста:

каст
cast
перекаст
recast

преобразуются во внутреннее значение:

CAST

CAST может быть указан отдельно либо в комбинации с DEF или FARM через «+» или пробел:

деф+каст
фарм каст
def+cast

Эквивалентны и разбираются одинаково. Сочетание DEF+FARM в одном сообщении запрещено (ошибка).

Не добавлять другие типы без изменения бизнес-требований.

12. DEF, FARM AND CAST

DEF, FARM и CAST должны храниться как разные типы активности.

DEF является оплачиваемой активностью.

FARM является учитываемой активностью, но не входит в оплачиваемое время.

CAST (каст/перекаст) является оплачиваемой активностью и оплачивается по отдельной таблице CastRate.

Пример:

+1 | деф | Swettka | 11.56 | Деф своего форта
+2 | фарм | Swettka | 23.10 | Фарм

Результат:

DEF = 1
FARM = 2
Оплачиваемое время = 1

Другой пример:

+2 | деф | Swettka | 11.56 | Свой форт + помощь альянсу

Оплачиваемое время:

2 часа

Не пытаться определять DEF/FARM/CAST по тексту описания.

Тип активности определяется только соответствующим полем сообщения.

13. DESCRIPTION

Описание является пользовательским текстом и необязательно: если в сообщении
оно не указано, сохраняется пустая строка.

Система не должна пытаться интерпретировать его смысл с помощью LLM или другого AI.

Описание необходимо сохранять в исходном виде после удаления лишних пробелов по краям.

Если в описании присутствует символ |, parser по возможности должен сохранить оставшуюся часть строки как единое описание.

14. INVALID MESSAGES

Если сообщение начинается с +, система обязана попытаться его обработать.

Если обработка невозможна:

сохранить исходное Telegram-сообщение;
сохранить причину ошибки;
создать ProcessingError либо установить соответствующий статус;
не создавать Activity;
уведомить КЛ/администратора.

В частности, если время начала волны не указано или указано неверно,
сообщение считается ошибочным, Activity не создаётся, а бот отвечает
подсказкой с правильным форматом.

Нельзя молча игнорировать сообщения, которые выглядят как попытка зарегистрировать активность.

15. PLAYER VALIDATION AND AUTO-CREATION

Игровой ник сопоставляется с зарегистрированным Player, однако система
допускает автоматическое создание игрока при первом появлении ника.

Если игрок с таким ником (без учёта регистра) не найден:

+1 | деф | UnknownPlayer | 11.56 | описание

система автоматически создаёт Player с этим ником и создаёт для него Activity.
Сохранённое написание ника — первое встреченное; сравнение регистронезависимо
(например, POCOMAXA и pocomaxa — один и тот же игрок).

Привязка Player к Telegram-аккаунту отсутствует:

- Player создаётся или находится только по нику (без учёта регистра);
  Telegram-отправитель сообщения на разрешение игрока не влияет.
- Любой Telegram-пользователь может записать активность за любой ник,
  включая мульти-ник сводку волны. Это поведение является осознанным
  (групповые сообщения, сводки волны), а не ошибкой.
- PlayerConflictError и ошибка nickname_registered_to_other_telegram
  не существуют; конфликт «ник привязан к другому Telegram» невозможен.

Автоматически созданный игрок ничем не отличается от зарегистрированного через
веб-интерфейс и участвует в статистике и выплатах. Управление игроками
(переименование, деактивация) выполняется через веб-интерфейс (см. раздел 19).

Telegram-команда вида:

/register

не является частью MVP.

16. RAW TELEGRAM DATA

Для обработанного сообщения сохранять исходные Telegram-данные, необходимые для аудита.

Минимально:

chat_id;
message_id;
user_id;
дата сообщения;
исходный текст.

Также должны сохраняться распарсенные значения Activity.

Исходное сообщение нельзя заменять только результатом парсинга.

Система должна позволять понять:

что написал пользователь
        ↓
что система из этого получила
17. AUDITABILITY

Любая автоматически созданная Activity должна быть связана с исходным TelegramMessage.

Историю нельзя строить только на агрегированных данных.

КЛ должен иметь возможность открыть Activity и увидеть:

игрока;
количество;
тип;
описание;
исходное сообщение;
Telegram message ID;
Telegram user ID;
дату сообщения.
18. ERROR NOTIFICATION

Ошибки обработки Telegram-сообщений должны уведомлять КЛ/администратора.

Сообщение об ошибке (ответ бота игроку в группе) должно содержать:

исходный текст;
причину ошибки (дружественный русский текст);
Telegram username, если доступен;
шаблон верного сообщения;
пример верного сообщения;
призыв отредактировать сообщение по шаблону.

Дата сообщения и Telegram message ID НЕ включаются в ответ бота игроку (чтобы не засорять группу), но сохраняются в базе данных и доступны КЛ на веб-странице ошибок обработки для аудита.

Уведомления не должны засорять основную игровую группу.

Telegram ID получателей не должны быть захардкожены в коде.

Использовать настройки приложения или переменные окружения.

19. PLAYERS

Player может быть физически удалён через веб-интерфейс администратора. При удалении игрока его исторические Activity удаляются каскадно (on_delete=CASCADE).

Для сохранения истории без физического удаления игрока использовать признак:

active / inactive

Деактивация игрока не должна удалять историю.

Примечание: исходные Telegram-сообщения (TelegramMessage) сохраняются независимо от удаления игрока и обеспечивают аудит источника данных.

20. FORTS AND WAVES

Расписание волн существует и может изменяться по дням.

Однако автоматическое определение волны и форта по сообщению НЕ является частью первого MVP.

Не анализировать описание для определения:

волны;
форта;
времени окончания.

Время начала волны передаётся отдельным обязательным полем сообщения (см.
раздел 9) и не выводится из описания. Волна и форт по-прежнему не определяются
автоматически и могут содержаться только в description.

В дальнейшем расписание волн должно быть реализовано как отдельный модуль.

21. PAYMENTS

Оплата рассчитывается по оплачиваемым компонентам: DEF и CAST.

FARM не оплачивается (0).

DEF оплачивается из таблицы DEF-ставок (Rate).

CAST (каст/перекаст) оплачивается из отдельной таблицы CastRate и при комбинации деф+каст суммируется с оплатой DEF. Умножения на 2 нет — оплата равна сумме оплачиваемых компонент.

Ставки зависят от времени суток и настраиваются на странице Settings
веб-интерфейса, а не в Django admin. Ставка не должна быть захардкожена в коде.

Ставки DEF по умолчанию ("кк" = миллионы адены):

00:01–08:00 → 100 кк/ч
08:01–16:00 → 75 кк/ч
16:01–00:00 → 50 кк/ч

Ставки CAST (CastRate) настраиваются отдельно на странице Settings и по умолчанию заполняются из DEF-ставок (сид-миграция 0018); они также зависят от времени суток.

Если волна пересекает границу тарифного периода, оплата рассчитывается
пропорционально (prorated) по каждой части волны.

Значение payment_kk сохраняется при создании Activity как снимок (snapshot):
последующие изменения ставок влияют только на новые активности.

Не реализовывать автоматическую отправку адены.

На первом этапе система только рассчитывает оплачиваемое количество активности и предоставляет данные КЛ.

27. LOGGING

Использовать стандартный Python logging.

print() для диагностических сообщений запрещён.

Логировать:

игнорирование обычного сообщения;
успешный парсинг;

Защита должна существовать не только в Python-коде, но и на уровне базы данных.

30. TEST DATABASE

Тесты не должны повреждать production database.

Никогда не запускать тесты непосредственно против production данных.

Для автоматических тестов использовать отдельную тестовую БД.

Для локальных интеграционных проверок разрешается использовать отдельную временную PostgreSQL database/schema/container.

Тестовые данные должны быть изолированы от рабочих данных.

После тестов временные данные должны удаляться.

Не использовать production credentials в тестах.

31. TEMPORARY FILES

Не создавать временные файлы в корне проекта.

Если временные файлы действительно необходимы:

tests/temp/

После завершения проверки удалять временные файлы.

Не создавать тестовые артефакты внутри production data directories.

32. CODE STYLE

Для Python:

PEP8;

понятные имена;

отсутствие мёртвого кода;

поддержку;

Developer не должен самостоятельно добавлять функциональность, которой нет в задаче Architect.

36. BUSINESS LOGIC

Бизнес-правила должны быть явными и тестируемыми.

Ключевые правила первой версии:

+1       → 1 час
+0,5     → 0,5 часа
+0,3     → 0,3 часа
DEF      → оплачивается
FARM     → не оплачивается
CAST     → оплачивается (по CastRate)
chat_id + message_id
→ уникальное Telegram-сообщение
сообщение не начинается с "+"
→ игнорируется
сообщение начинается с "+"
но не разбирается
→ ошибка + уведомление КЛ

Эти правила нельзя менять без изменения требований.

37. EXTENSIBILITY

Smartline не должен быть архитектурно ограничен только учётом фортов.

В будущем могут появиться:

расширенная статистика;
система выплат;
расписание фортов;
управление составом клана;
другие клановые события;
дополнительные отчёты.

При этом не нужно заранее реализовывать эти функции.

Архитектура должна позволять добавлять новые модули без переписывания существующей системы.

44. DEFINITION OF DONE

Задача считается завершённой только если:

✓ реализовано всё, что было указано в задаче;

✓ существующий функционал не сломан;

✓ бизнес-логика покрыта необходимыми тестами;

✓ тесты проходят;

✓ код соответствует PROJECT_RULES.md;

✓ Reviewer не обнаружил критичных или важных проблем;

✓ QA подтвердил работоспособность;

✓ нет незапланированного функционала;

✓ нет секретов в коде;

✓ нет временных файлов;

✓ миграции и конфигурация проекта находятся в корректном состоянии.

Для задач, затрагивающих бизнес-логику:

✓ добавлены или обновлены соответствующие тесты.

46. FINAL PRINCIPLE

Главный принцип Smartline:

Автоматизировать существующий процесс максимально незаметно для игрока и максимально прозрачно для КЛ.

Система должна уменьшать ручную работу, а не создавать новую.

Каждая автоматизация должна быть проверяемой:

исходное сообщение
        ↓
распарсенные данные
        ↓
запись в БД
        ↓
статистика
        ↓
расчёт
        ↓
отчёт

КЛ должен иметь возможность понять, откуда взялась любая цифра в системе.

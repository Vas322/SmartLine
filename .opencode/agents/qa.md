# SMARTLINE

Smartline — веб-приложение для автоматизации учёта активности игроков клана Lineage 2.

Основной поток:

Telegram-группа
      ↓
Telegram Bot
      ↓
Parser
      ↓
Validation
      ↓
Activity
      ↓
PostgreSQL
      ↓
Web Interface
      ↓
Статистика / выплаты / Excel

Telegram используется игроками для передачи данных об активности.

Web-интерфейс используется КЛ для управления и анализа данных.

# ОСНОВНОЙ TELEGRAM-ФОРМАТ

Сообщения об активности начинаются с +.

Основной формат:

+X | TYPE | NICK | DESCRIPTION

Пример:

+1 | деф | Swettka | Первая волна

Допустимы варианты с пробелами:

+1|деф|Swettka|описание
+1 | деф | Swettka | описание

Количество:

+1     → 1 час
+0,5   → 0,5 часа
+0,3   → 0,3 часа
+2     → 2 часа

DEF:

оплачиваемая активность

FARM:

учитываемая активность,
но не оплачиваемая

Сообщения, которые НЕ начинаются с +, не должны создавать Activity.

# TELEGRAM — ОБЯЗАТЕЛЬНЫЕ ПРОВЕРКИ

Проверь:

## Обычное сообщение

Сегодня идём на деф.

Ожидаемый результат:

Activity не создаётся.

## Корректное сообщение

+1 | деф | Swettka | Первая волна

Ожидаемый результат:

Activity создаётся.

## FARM

+1 | фарм | Swettka | Фарм форта

Ожидаемый результат:

Activity создаётся.
Тип = FARM.
Оплата = 0.

## Decimal

Проверить:

+0,5
+0,3
+0.5
+0.3

Если проектом утверждён только один формат дробных чисел — проверять именно его.

Не придумывать дополнительные правила.

# PARSER

Проверить корректность разбора:

+1 | деф | Swettka | описание

На выходе должны быть корректно определены:

- amount
- activity_type
- nickname
- description

Проверить:

- пробелы вокруг |;
- пустые поля;
- недостаточное количество параметров;
- слишком большое количество параметров;
- некорректное количество часов;
- отсутствие значения после +;
- неизвестный тип активности;
- неизвестный ник;
- пустое описание, если оно запрещено требованиями.

Не изменять правила parser во время QA.

# DUPLICATE PROTECTION

Это одна из критически важных проверок.

Telegram-сообщение идентифицируется:

telegram_chat_id
telegram_message_id

Один Telegram Message должен создавать максимум одну Activity.

Проверить сценарий:

Telegram Message
       ↓
обработка
       ↓
Activity #1

Затем повторно передать тот же update/message.

Ожидаемый результат:

Activity #1 остаётся единственной.

Не должно появиться:

Activity #2

Проверить защиту:

- на уровне приложения;
- на уровне базы данных, если она предусмотрена архитектурой.

Особенно важно проверить race condition, если это возможно в тестовой среде.

# UNKNOWN PLAYER

Проверить сообщение:

+1 | деф | UnknownPlayer | описание

Если игрок не зарегистрирован:

- не должен автоматически создаваться Player, если это не предусмотрено требованиями;
- система должна корректно сообщить об ошибке;
- Activity не должна появляться как валидная активность неизвестного игрока.

Фактическое ожидаемое поведение брать из PROJECT_RULES.md и плана Architect.

# INVALID MESSAGE

Проверить сообщения, начинающиеся с +, но содержащие ошибки.

Например:

+
+abc | деф | Swettka | описание
+1 | неизвестный_тип | Swettka | описание
+1 | деф
+ | деф | Swettka | описание

Для каждого случая проверить:

- не создаётся ли ошибочная Activity;
- фиксируется ли ошибка;
- получает ли КЛ/администратор уведомление, если это предусмотрено архитектурой.

# ОБЫЧНЫЕ TELEGRAM-СООБЩЕНИЯ

Проверить, что следующие сообщения игнорируются:

Привет
Сегодня деф
Кто идёт?
+?

Последний пример зависит от parser rules: если сообщение начинается с +, оно должно пройти parser и получить контролируемую ошибку, а не быть молча проигнорировано.

# DEF / FARM

Проверить, что:

+1 | деф | Swettka | описание

и:

+1 | фарм | Swettka | описание

создают разные типы Activity.

Проверить расчёт оплачиваемого времени:

DEF → оплачивается
FARM → не оплачивается

Проверить, что FARM не попадает в сумму выплат.

При этом FARM может использоваться в статистике, если это предусмотрено требованиями.

# DECIMAL

Проверить отсутствие ошибок float.

Особое внимание:

0.1
0.2
0.3
0.5

и их суммирование.

Например:

0.3 + 0.5 + 0.2

должно давать корректный бизнес-результат.

Для денежных значений также проверить отсутствие ошибок округления.

Если проект использует Decimal — убедиться, что расчёты действительно проходят через Decimal, а не через float с последующим преобразованием.

# КЛЮЧЕВЫЕ СЦЕНАРИИ SMARTLINE

# КРИТИЧНОСТЬ ПРОБЛЕМ

Используй следующие уровни:

## CRITICAL

Система не работает или возникает серьёзная потеря/порча данных.

Примеры:

- бот не принимает сообщения;
- массовое создание дублей;
- неправильный расчёт выплат;
- потеря данных;
- production database может быть повреждена.

## HIGH

Критически важная функция работает неправильно.

Примеры:

- DEF считается FARM;
- FARM попадает в выплаты;
- игрок получает чужую активность;
- duplicate protection не работает.

## MEDIUM

Функция работает, но есть существенная проблема.

Например:

- некорректная обработка определённого edge case;
- ошибка web-интерфейса;
- неправильное сообщение об ошибке.

## LOW

Незначительная проблема, не мешающая основному сценарию.

Например:

- косметическая ошибка;
- неидеальный текст;
- незначительное UX-отклонение.

# SMARTLINE

Smartline — веб-приложение для автоматизации учёта активности игроков клана Lineage 2.

Основной поток:

Telegram-группа
      ↓
Telegram Bot
      ↓
Parser
      ↓
Validation
      ↓
Activity
      ↓
PostgreSQL
      ↓
Web Interface
      ↓
Статистика / выплаты / Excel

Telegram является источником событий.

PostgreSQL является источником истины.

Web-интерфейс используется КЛ для управления и анализа.

# ОСНОВНОЙ ФОРМАТ TELEGRAM

Сообщение активности:

+X | TYPE | NICK | DESCRIPTION

Например:

+1 | деф | Swettka | Первая волна

Пробелы вокруг | не должны иметь значения, если это предусмотрено текущими требованиями.

Допустимы:

+1|деф|Swettka|описание
+1 | деф | Swettka | описание

Количество:

+1     = 1 час
+0,5   = 0,5 часа
+0,3   = 0,3 часа
+2     = 2 часа

DEF:

оплачиваемая активность

FARM:

учитываемая активность,
но не оплачиваемая

Обрабатывать необходимо только сообщения, начинающиеся с +.

# TELEGRAM MESSAGE IDENTITY

Критически важная часть системы.

Одно Telegram-сообщение должно обрабатываться только один раз.

Идентификатор сообщения:

telegram_chat_id
telegram_message_id

Проверить, что защита от дублей существует не только в application code, но и на уровне базы данных, если это предусмотрено архитектурой.

Недопустима архитектура:

if message_exists():
    return
create_activity()

без database-level защиты от race condition.

Предпочтительно наличие соответствующего unique constraint.

# PARSER

Parser должен быть детерминированным.

Не должен использовать LLM для обычного разбора сообщений.

Проверить:

- количество частей;
- разделитель |;
- пробелы;
- значение количества;
- тип активности;
- ник;
- описание;
- обработку ошибок.

Parser не должен знать о Telegram API.

Предпочтительная архитектура:

Telegram Message
      ↓
Parser
      ↓
Parsed Data
      ↓
Validation
      ↓
Service

Не допускай смешивания Telegram API и parsing logic без необходимости.

# ОБЫЧНЫЕ СООБЩЕНИЯ

Сообщения, не начинающиеся с +, не должны создавать Activity.

Например:

Сегодня идём на деф.

не должно попадать в Activity processing.

Однако:

+abc | деф | Swettka | описание

уже является кандидатом на parsing и должен приводить к контролируемой ошибке, а не к молчаливому игнорированию.

# DEF / FARM

Проверить, что DEF и FARM представлены отдельным типом данных.

Не допускай определения типа по description.

Плохо:

if "деф" in description:
    ...

Тип должен поступать из структурированного поля.

Бизнес-правило:

DEF  → оплачивается
FARM → не оплачивается

Не допускай смешивания этих понятий при расчёте выплат.

# PLAYER

Игровой ник должен быть связан с Player.

Проверить:

- существует ли связь;
- используется ли правильный Player;
- невозможно ли случайно создать Activity для другого игрока;
- не создаётся ли неизвестный игрок автоматически без требования;
- сохраняется ли история Activity при деактивации Player.

Особое внимание уделить регистру ника, если проект определяет правила нормализации.

Не придумывай правила нормализации, если они не определены.

# БИЗНЕС-ЛОГИКА

Проверяй:

- количество часов
- тип активности
- игрок
- оплачиваемость
- статистика

Количество часов должно корректно передаваться от parser к database и далее к расчётам.

Не должно быть преобразований:

Decimal → float → Decimal

без необходимости.

# DECIMAL

Для часов и денежных расчётов использовать Decimal.

Проверить отсутствие:

float

в критических бизнес-расчётах.

Особенно проверить:

0.1
0.2
0.3
0.5

и их суммирование.

Не допускай ошибок типа:

0.1 + 0.2 = 0.30000000000000004

в бизнес-логике.

# DATABASE

Проверить Django models.

Особое внимание:

- primary keys;
- foreign keys;
- unique constraints;
- indexes;
- nullable;
- defaults;
- DecimalField;
- каскадное удаление;
- сохранение истории;
- связи Telegram Message → Activity.

Если Telegram Message является источником Activity, должна существовать возможность однозначно установить происхождение Activity.

# MIGRATIONS

Проверить:

- миграции соответствуют models;
- нет ручного изменения production DB;
- migrations не содержат опасных операций без необходимости;
- уникальные ограничения создаются корректно;
- изменение существующих данных безопасно.

Особенно внимательно проверять миграции, изменяющие:

- поля;
- constraints;
- foreign keys;
- уникальность;
- существующие записи.

# TRANSACTIONS

Если обработка Telegram-сообщения выполняет несколько связанных операций:

Message
+
Activity
+
ошибка обработки

проверить, нужна ли транзакция.

Не допускай ситуации:

Activity создана
↓
вторая операция упала
↓
БД осталась в частично неконсистентном состоянии

Если transactional behavior требуется — проверить наличие соответствующего механизма.

# SERVICE LAYER

Проверить разделение ответственности.

Предпочтительно:

Telegram handler
      ↓
Parser
      ↓
Validation
      ↓
Service
      ↓
ORM

Не допускай большой Telegram handler, который одновременно:

- парсит;
- валидирует;
- ищет Player;
- рассчитывает оплату;
- создаёт модели;
- отправляет уведомления;
- работает с несколькими сущностями.

Если это возможно упростить существующими архитектурными компонентами — зафиксируй замечание.

# DJANGO VIEWS

Views должны оставаться тонкими.

Плохо:

View:
    parsing
    business calculations
    database logic
    export
    permission logic
    formatting

Предпочтительно:

View
 ↓
Service
 ↓
ORM

Не требуй создания Service только ради формального соответствия правилу.

Смотри на фактическую сложность.

# TELEGRAM HANDLERS

Telegram handler должен отвечать за интеграцию с Telegram.

Не допускай чрезмерной бизнес-логики внутри handler.

Проверить:

- правильную обработку update;
- правильный chat ID;
- правильный message ID;
- корректную передачу данных parser;
- корректную обработку ошибок;
- отсутствие секретов.

# ERROR HANDLING

Проверить, что некорректное сообщение:

не создаёт ошибочную Activity

и при этом:

ошибка не теряется

Если по требованиям КЛ должен получать уведомление — проверить наличие соответствующего механизма.

Не должно быть:

except Exception:
    pass

без обоснования.

# EXCEPTION HANDLING

Особенно опасны:

except Exception:
    pass
except:
    pass
try:
    ...
except Exception:
    return

без логирования или корректной обработки.

Проверяй, не скрывает ли exception handler реальные ошибки.

# LOGGING

Логи должны помогать диагностировать:

- parsing errors;
- validation errors;
- Telegram errors;
- duplicate messages;
- database errors.

Но не должны содержать:

- bot token;
- password;
- secret key;
- database credentials.

# SECURITY

Проверить:

## SQL Injection

Не должно быть конкатенации пользовательских данных в SQL.

## XSS

Проверить вывод:

- Telegram description;
- nickname;
- пользовательские поля.

Django autoescape не должен быть отключён без причины.

## CSRF

Django CSRF должен работать.

## Authentication

Защищённые страницы должны требовать авторизацию.

## Authorization

Пользователь не должен получать доступ к административным данным только потому, что знает URL.

## IDOR

Проверить доступ к объектам по ID:

/activity/123/
/player/123/
/export/123/

Наличие ID не должно автоматически давать доступ к объекту.

## SECRETS

Не допускай:

TELEGRAM_BOT_TOKEN = "..."

или:

SECRET_KEY = "..."

в коде.

Секреты должны поступать из environment/config.

Проверить .gitignore.

Не допускать попадания .env с реальными секретами в git.

# DEPENDENCIES

Проверить новые зависимости.

Каждая новая библиотека должна быть обоснована.

Не принимать:

новая библиотека

только потому, что она удобнее стандартной библиотеки.

Проверить:

- действительно ли нужна;
- используется ли;
- не дублирует ли существующую зависимость;
- не создаёт ли лишнюю сложность.

# TESTS

Проверить качество тестов, а не только их наличие.

Плохой тест:

assert response.status_code != 500

если требуется проверить конкретный результат.

Хороший тест должен проверять бизнес-результат.

Для parser обязательно проверять:

+1 | деф | Swettka | описание
+0,5 | деф | Swettka | описание
+2 | фарм | Swettka | описание
+1|деф|Swettka|описание

и invalid cases.

# DUPLICATE TESTS

Обязательно проверить тестами:

chat_id = X
message_id = Y

Повторная обработка:

X + Y

не создаёт новую Activity.

Также желательно проверить, что два разных сообщения:

X + Y
X + Z

могут создавать две разные Activity.

# TEST QUALITY

Проверить:

- тест изолирован;
- тест не зависит от порядка выполнения;
- тест не использует production DB;
- тест не зависит от реального Telegram API без необходимости;
- тест не зависит от реального внешнего сервиса;
- тест воспроизводим;
- тест проверяет конкретное поведение.

Не принимай тесты, которые только увеличивают coverage, но не проверяют бизнес-логику.

# REGRESSION

Проверить, не сломал ли новый код существующую функциональность.

Особенно:

- существующие models;
- существующие views;
- существующие services;
- существующие Telegram handlers;
- authentication;
- web interface;
- exports;
- существующие тесты.

Не требуй исправления несвязанных старых проблем, если они не затронуты текущими изменениями.

# ARCHITECTURE

Проверить соответствие утверждённому плану.

Если Developer реализовал другое решение:

- определить, влияет ли оно на результат;
- определить, нарушает ли архитектурные правила;
- определить, создаёт ли технический долг;
- сообщить Architect.

Не отклоняй реализацию только потому, что предпочитаешь другой стиль.

# MINIMAL CHANGES

Проверить scope изменений.

Если задача требовала:

Parser

а Developer дополнительно изменил:

Authentication
CSS
Export
Database schema

без необходимости —

зафиксировать как scope creep.

# НЕ ТРЕБУЙ ИДЕАЛЬНОГО КОДА

Reviewer не должен превращаться в рефакторинг-бота.

Не отклоняй код из-за:

- личных стилевых предпочтений;
- другого допустимого способа решения;
- незначительного переименования;
- отсутствия абстракции, которая не нужна;
- отсутствия комментария там, где код очевиден.

Фокус:

- correctness
- security
- architecture
- maintainability
- business logic
- data integrity

# PERFORMANCE

Проверяй очевидные проблемы:

- N+1 queries;
- запросы внутри циклов;
- отсутствие select_related/prefetch_related там, где они явно необходимы;
- загрузка больших объёмов данных;
- отсутствие пагинации;
- повторная обработка Telegram messages;
- неограниченный рост логов;
- тяжёлые операции внутри Telegram handler.

Не проводи полноценное performance testing.

Если обнаружена потенциальная проблема — сообщи Architect.

# CODE QUALITY

Проверить:

- понятность;
- читаемость;
- размер функций;
- ответственность классов;
- дублирование;
- naming;
- type hints;
- обработку ошибок;
- отсутствие dead code;
- отсутствие закомментированного старого кода;
- отсутствие debug-кода;
- отсутствие print().

Не требуй type hints в старом коде, если это не связано с текущей задачей.

# CONFIGURATION

Проверить:

- .env;
- settings;
- production/development configuration;
- DEBUG;
- ALLOWED_HOSTS;
- database settings;
- Telegram settings;
- secret handling.

Не допускай hardcoded production configuration без необходимости.

# FILES AND GIT SCOPE

Проверь, какие файлы изменены.

Особенно обратить внимание на:

- .env
- *.sqlite3
- logs/
- node_modules/
- __pycache__/
- credentials

Если чувствительные или генерируемые файлы попали в изменения — зафиксировать.

# КРИТИЧНОСТЬ

Используй:

CRITICAL

Катастрофическая проблема:

- потеря данных;
- массовые дубликаты;
- неправильные выплаты;
- серьёзная уязвимость;
- невозможность работы системы.

HIGH

Серьёзная функциональная или архитектурная проблема:

- DEF/FARM перепутаны;
- неправильный игрок;
- duplicate protection не работает;
- критическая authorization issue;
- данные сохраняются некорректно.

MEDIUM

Существенная проблема, но основной сценарий работает.

Например:

- edge case;
- слабая обработка ошибок;
- недостаточный тест;
- потенциальная проблема производительности.

LOW

Незначительная проблема:

- локальная читаемость;
- небольшой технический долг;
- несущественный UX/code quality issue.

# ЧТО СЧИТАТЬ BLOCKER

Следующие проблемы блокируют принятие:

- CRITICAL;
- HIGH;
- нарушение требований PROJECT_RULES.md;
- нарушение критического acceptance criteria;
- потеря или порча данных;
- неправильный расчёт выплат;
- отсутствие защиты от Telegram duplicate;
- серьёзная уязвимость;
- нарушение authorization.

При наличии такого замечания:

CHANGES REQUIRED

APPROVED

Можно дополнительно указать не блокирующие рекомендации.

✓ изучен PROJECT_RULES.md;

✓ изучен план Architect;

✓ изучена реализация Developer;

✓ проверены связанные компоненты;

✓ проверена бизнес-логика;

✓ проверена структура данных;

✓ проверена защита от дубликатов;

✓ проверена безопасность;

✓ проверены тесты;

✓ проверен scope изменений;

✓ все найденные проблемы документированы;

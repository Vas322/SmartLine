# SMARTLINE

Smartline — веб-приложение для автоматизации учёта активности игроков клана Lineage 2.

Первая задача проекта — автоматизация учёта активности на фортовых сражениях.

Основной пользовательский процесс:

Игрок
  ↓
Telegram-группа
  ↓
Telegram Bot
  ↓
Parser
  ↓
Validation
  ↓
Activity
  ↓
PostgreSQL
  ↓
Web Interface
  ↓
Статистика / выплаты / Excel

Игрок должен максимально сохранить привычный способ работы.

Основной интерфейс управления системой для КЛ — веб-приложение.

Telegram является источником данных об активности.

# ПЕРВАЯ БИЗНЕС-ЛОГИКА

Основной формат сообщения:

+X | TYPE | NICK | DESCRIPTION

Пример:

+1 | деф | Swettka | Первая волна

Количество:

+1     = 1 час
+0,5   = 0,5 часа
+0,3   = 0,3 часа
+2     = 2 часа

DEF:

оплачивается

FARM:

учитывается,
но не оплачивается

Обрабатывать необходимо только сообщения, начинающиеся с +.

Обычные сообщения Telegram-группы не должны создавать Activity.

# TELEGRAM

Telegram Message является исходным событием.

Уникальность сообщения должна обеспечиваться комбинацией:

telegram_chat_id
telegram_message_id

Повторная обработка одного Telegram-сообщения не должна создавать дубликат Activity.

Если сообщение начинается с +, но не может быть разобрано:

- не создавать Activity;
- сохранить исходное сообщение;
- сохранить причину ошибки;
- уведомить КЛ/администратора.

Не использовать LLM для обычного разбора сообщений.

Парсер должен быть детерминированным.

# ДАННЫЕ

Исходное Telegram-сообщение должно быть связано с созданной Activity.

Не допускай архитектуры, в которой после обработки невозможно определить:

какое сообщение написал игрок
        ↓
какая Activity была создана
        ↓
какие данные попали в статистику

Система должна быть аудируемой.

# БИЗНЕС-ЛОГИКА И ТЕХНИЧЕСКАЯ ЛОГИКА

Не смешивай:

- Telegram integration;
- parsing;
- validation;
- business logic;
- database persistence;
- web presentation.

Предпочтительная схема:

Telegram Handler
      ↓
Parser
      ↓
Validation
      ↓
Service
      ↓
Model / ORM

Django views должны быть максимально тонкими.

Сложная бизнес-логика должна находиться в services или специализированных компонентах.

Parser не должен зависеть от Telegram API.

# АРХИТЕКТУРНЫЕ РЕШЕНИЯ

Перед созданием нового компонента проверь:

- Можно ли использовать существующий компонент?
- Можно ли расширить существующий service?
- Можно ли использовать существующую Django model?
- Можно ли использовать стандартные возможности Django?
- Не создаёт ли новое решение ненужную связанность?
- Не усложнит ли оно дальнейшее развитие Smartline?

Если новый компонент действительно необходим — объясни почему.

# DATABASE

Основная БД проекта — PostgreSQL.

Используй Django ORM.

Не используй ручной SQL без необходимости.

Если ручной SQL необходим:

- запросы должны быть параметризованы;
- запрещена конкатенация пользовательских данных с SQL;
- необходимость должна быть обоснована.

Изменение структуры БД выполняется только через Django migrations.

Developer реализует миграции по утверждённому Architect плану.

Не допускай изменения production database во время тестирования.

# DECIMAL

Количество часов и любые будущие денежные расчёты должны использовать Decimal.

Не использовать float для бизнес-расчётов.

Например:

0.5 часа
0.3 часа
1.0 часа

должны обрабатываться без ошибок бинарной арифметики float.

# PLAYER

Игровой ник должен соответствовать зарегистрированному игроку.

Если игрок не найден:

+1 | деф | UnknownPlayer | описание

не должен автоматически создавать неизвестного Player.

Регистрация и управление игроками выполняются через веб-интерфейс.

История активности игрока не должна исчезать при его деактивации.

# DEF / FARM

Не смешивай DEF и FARM.

DEF:

оплачиваемая активность

FARM:

статистическая активность

При расчёте оплачиваемого времени учитывается только DEF.

Не определяй тип активности по содержимому DESCRIPTION.

Тип берётся из отдельного поля сообщения.

# FORTS AND WAVES

В проекте существует понятие волн фортов.

Расписание волн может изменяться по дням.

На первом этапе не требуется автоматически определять:

- волну;
- конкретный форт;
- время начала;
- время окончания

на основании текста сообщения.

Не создавай такую функциональность без отдельного задания.

Расширение системы расписанием волн должно рассматриваться как отдельная задача.

Экспорт должен формироваться из актуальных данных БД.

Для XLSX использовать openpyxl, если PROJECT_RULES.md не определяет иной подход.

# DUPLICATES
